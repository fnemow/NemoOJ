# NemoOJ 上线前完善与 Agent 执行文档

编制日期：2026-09-17。本文是实施任务书，不代表这些任务已经完成或通过验收。

## 1. 目标与范围

目标：让项目可以从干净环境构建、部署，在受控资源下可靠完成判题，并在依赖故障或进程重启后恢复，具备发布、观察和回滚能力。

默认上线范围：`OJ-backend-microservice`（网关、用户、题目、判题服务及共享模块）和 `nemo-sandbox`。`backend` 暂作为历史单体实现与现有 SQL 来源；不删除、不同步重构、不与微服务同时上线。若后续用户明确选择单体方案，应重新调整任务范围。

语言范围更新（2026-09-17，用户已确认）：保留 Java，新增 CPython 3.12 与 GCC 14 / C++17，三种语言均覆盖 ACM 与函数模式，分阶段实施。具体设计与验收见 [多语言判题扩展方案](introduction/MultiLanguage.md)；替代原“首发仅 Java、不扩展语言”的约定，尚不代表已实现。保留 Redis Session，不为本次上线强行改为 JWT；不引入 Kubernetes、不进行无关框架重写。

前端范围更新（2026-09-17，用户已确认设计方向）：新增独立前端建设任务，采用 Vue 3 / TypeScript / Vite / Element Plus / Monaco，包含题库、做题工作台、提交记录、个人中心和管理后台。组件、视觉、接口补齐与验收见 [前端设计与 Agent 实施规范](introduction/FrontendDesign.md)，替代原“不新增前端”的约定。该文档是实施设计，不代表前端或新增接口已完成；后端 T04/T08 等安全与判题门槛仍适用。

本文中的路径相对于项目根目录。执行前重新核实源码；已完成的事项应记录验证证据，不要重复修改。

已有基础：BCrypt、Docker 非 root 用户及网络隔离、只读根文件系统、内存/PID/输出限制、源文件路径校验、消息持久化、CAS 抢占及死信队列。必须保留并回归验证。

已从源码确认：

| 编号 | 现状 | 主要证据位置 |
|---|---|---|
| E01 | 默认配置仍含本机依赖地址和明文凭据；沙箱 prod 端口为 8101，而判题端默认访问 8090 | 各服务 `src/main/resources/application*.yml` |
| E02 | 沙箱鉴权回退到固定密钥；调用方与服务端配置键不同 | `nemo-sandbox/.../controller/SandboxController.java`、判题服务 `application.yml` |
| E03 | 应用模块 Spring Boot 插件跳过 repackage | 微服务应用模块及 `nemo-sandbox/pom.xml` |

| E05 | 判题中提交收到重复消息直接返回；结果写回缺少执行代次保护 | 判题服务 `judge/JudgeServiceImpl.java`、题目服务 `controller/inner/QuestionInnerController.java` |

尚需验证：真实 Linux Docker 行为、网络暴露情况、部署平台已有防护、数据库存量数据、生产容量及最终 JAR 启动。之前离线 Maven 测试因缺少依赖 BOM 未进入测试执行阶段；这不是源码编译失败或测试失败的证明。

## 3. Agent 执行规则

1. 先读取适用的 `AGENTS.md`（若有）、`record/rules.md`、相关修改记录及本文件。检查各子目录 Git 状态，不覆盖用户未提交修改；根目录此前不是 Git 仓库，不据此擅自初始化仓库。
2. 按下方阶段顺序执行，每个任务先检查现状、实施最小完整变更、运行相关验证，再更新任务状态。不得只改配置示例而不修改实际生效路径。
3. 状态只能是：未开始、进行中、代码完成待验证、已验收、阻塞。只有验收证据齐全才标记已验收；环境不足不得写“通过”。
4. 跨服务接口、数据库和状态机修改必须同步更新所有调用方、映射、配置及测试。保留公共 API 与现有状态值；如必须破坏兼容，先写清迁移路径。
5. 每次代码修改按 `record/rules.md` 写入 `record/log/`；引入新机制或技术时写入 `record/introduction/`。禁止把真实密钥写入源码、日志、报告或提交。
6. 可自主完成本地代码、测试、部署模板和文档。本文不授权操作生产数据库、清除存量数据、轮换线上凭据、实际发布或购买资源；这些操作先形成可审查脚本与影响说明，再按用户授权执行。
7. 不因缺少生产域名、服务器 IP、密钥而停止独立实现：使用明确的变量占位及生产启动校验。依赖环境的验收列为待验证。
8. 不通过关闭测试、取消鉴权、开启 native 沙箱、使用 privileged 容器或全局 root 来让测试通过。测试专用替代配置不得进入 prod。
9. 暂不主动启动其他 agent。若用户另外授权并行工作，先分配互不冲突的模块；共享模型、SQL 和状态机由一个执行者统筹。

### 4.1.1 当前验收结论（2026-09-17）

**全部 13 个任务状态为「代码完成待验证」，无一标记「已验收」。**

原因：最低验收矩阵中 A10（判题正确性）、A11（恶意资源）、A13（容器清理）
因本机无 Linux + Docker 而未执行；A14（HTTPS）、A15（备份与回滚演练）、
A12（压测）缺少预发环境。按本文第 3 节规则，环境不足不得写"通过"。

完整矩阵、证据与阻塞项见 **[上线前验收报告](pre-release-acceptance.md)**，
其中给出的结论是**暂不发布**，并列出补做条件。

本地已验证部分：94 个自动化测试全部通过（单元 71 + 集成 23）；
执行过程中发现并修复了 20 余个真实缺陷（含构建静默跳过测试、
Spring 6 参数名失效、Redis Session 实际未接入等）。

### 4.2 已确认的环境约束（影响后续任务验收口径）

本机可用的中间件：**MySQL 8.0、RabbitMQ、Redis 均在本机运行**。
缺失：**Nacos、Docker**。因此：

- 依赖 Nacos 的跨服务 Feign 真实调用链，本地无法端到端验证；
- 依赖 Docker 的沙箱容器执行（T08）无法在本机验证；
- 上述两项必须在具备对应环境的主机上补做，`预发布验收` 结论需如实标注。

### 4.3 执行中发现、待后续任务处理的缺陷

## 5. 任务详细要求

### T01：构建与发布产物

修改范围：微服务父/子 POM、沙箱 POM、构建说明、CI 配置。

- 明确并记录构建 JDK、Maven 和沙箱内 Java 运行时版本；检查实际构建环境再选择兼容版本，不盲目全量升级。
- 应用模块生成可执行 JAR；共享模型、common、service-client 继续生成普通依赖 JAR，不把它们重新打包成 Boot 应用。
- 显式保证 JUnit 测试被构建插件识别，核对实际执行数量；建立干净构建流程，不能依赖现存 `target/`。
- 增加依赖安全扫描与产物版本标识。实际扫描后再列出漏洞、影响及修复选择，不根据旧版本号直接宣称存在特定漏洞。

验收：从干净输出目录构建成功；报告测试数量与结果；每个应用用最终 JAR 在测试环境启动并通过健康检查；没有未解释的零测试或跳过测试。

### T02：生产配置和密钥

修改范围：各应用 `application*.yml`、配置类、启动校验、部署环境变量示例。

- 明确 dev/test/prod 配置边界；数据库、Redis、RabbitMQ、Nacos、沙箱地址均可外部注入。prod 缺少关键配置时失败退出，不能悄悄回退到示例凭据。
- 统一沙箱端和判题端密钥映射，移除固定默认值。示例只包含占位符；生产密钥轮换列入运维操作，不由代码修改代替。
- 约定网关 8101、用户 8102、题目 8103、判题 8104、沙箱 8090，或选择另一套明确一致的映射；最终值以部署模板和调用地址一致为准。
- 生产关闭 SQL 明文输出与公开接口文档，保留受控诊断能力；配置实际域名的 CORS 白名单和 HTTPS 下 Cookie 安全属性，验证 Session 跨服务可用。

验收：prod 缺少密钥必定启动失败；显式配置后全部服务可启动；错误密钥不能调用沙箱；配置及产物无真实凭据；实际沙箱 URL 可达。

### T03：数据库迁移基础与账号约束

- 将现有建表与增量 SQL 整理为有序、可追踪的迁移方案；为新库和存量库分别给出执行方式。不同时引入两套迁移工具。
- 先提供重复账号检测 SQL，再添加数据库唯一约束。默认软删除后账号仍保留占用，避免隐式账号重用；如现有产品规则不同，明确记录后调整。
- 数据库排序规则与账号归一化规则保持一致。捕获唯一键冲突并返回稳定业务错误，不依赖单机 `synchronized` 保证唯一。
- 若存在重复账号，输出冲突记录处理方案，不自动删除或合并账号。新建 outbox、租约等字段时由对应任务提供独立增量迁移。

验收：两个实例并发注册同一账号只产生一条有效记录；新库初始化和存量升级均成功；有冲突数据时迁移安全失败并给出可操作提示。

### T04：内部接口与网络边界

- 网关保留内部路径拦截；业务服务对 `/inner/**` 独立验证服务凭据，Feign 调用方自动附加凭据，外部请求不得通过伪造透传头获得权限。
- 核查所有内部接口及替代路径，公共接口继续执行用户登录和角色校验；不能用服务凭据替代终端用户权限判断。
- 部署只公开 HTTPS 入口。业务端口、沙箱、数据库、Redis、RabbitMQ、Nacos、Docker daemon 均限制在所需内部网络；管理控制台按需受控访问。
- 默认维持现有 Redis Session，验证登录、退出、管理员权限和跨服务调用；明确 CSRF 防护策略，不能把 CORS 白名单当成全部防护。

验收：外网及网关不能到达内部接口；直接访问业务服务内部接口时，无凭据/错误凭据均被拒绝，合法服务调用成功；未登录与普通用户不能越权。

### T05：可靠消息投递

推荐使用同库事务 outbox，实现“至少一次投递 + 幂等消费”，不要宣称 MQ 恰好一次。

- 在同一个数据库事务里写提交记录和 outbox 事件。消息记录至少具备事件 ID、提交 ID、状态、重试次数、下次尝试时间及投递租约信息。
- 后台投递器支持多实例竞争，处理 publisher confirm ACK/NACK、return、超时和不可路由；不能把 `convertAndSend` 返回当作 broker 确认。
- 成功判定必须同时满足确认和正确路由，处理异步回调竞态。ACK 后数据库更新失败允许重发，由消费者幂等兜底。
- 有界退避、失败告警、投递租约回收；长期失败任务进入可人工重试的持久记录。不得只记录日志后丢弃。
- 保留持久消息与持久队列；补上待判题超时对账，能够解释每条未完成提交当前的归属。

验收：提交事务回滚时没有可投递事件；提交落库后杀进程、MQ 离线、路由不存在、confirm 超时、确认后杀进程均不会静默丢任务；重复投递不产生重复最终结果。

### T06：判题租约、恢复与死信闭环

- 保留现有对外状态值，在内部增加执行代次/令牌、租约到期时间、尝试次数及必要错误信息。原子抢占 WAITING 并产生新令牌。
- 明确总执行预算、心跳周期及租约关系。长任务续租；过期任务由回收器条件更新并可靠重新入队；超过最大次数进入明确系统错误终态。
- 结果提交、异常回退、续租和死信标记必须同时校验提交 ID、状态及执行令牌。禁止旧消费者迟到结果覆盖新执行或已完成结果。
- 对正在执行的重复消息可结束消费，但必须保证有效租约及独立恢复器可以接管失联任务；终态消息直接幂等返回。
- 死信更新异常不能吞掉后自动确认。采用有界重试与持久失败记录，不使用无限立即 requeue。重复/过期死信不能覆盖成功结果。
- 中断与优雅停机路径明确处理；不能在业务结果未持久化时将其误报为完成。

验收：抢占后强杀进程能在规定时间内恢复；长任务不会误回收；旧执行迟到写回被拒绝；重复消息和重复死信不改变终态；数据库或 Feign 暂时故障后最终收敛。记录恢复时间上界及配置依据。

### T07：题目发布权限与不可变快照

- 公共列表、详情及提交接口只允许访问已发布题目；草稿仅作者/管理员通过明确授权的管理路径访问。查询参数不得绕过限制。
- 核查答案、隐藏用例及其他用户源码脱敏，以真实响应 JSON 验证，不只检查注释。
- 默认采用不可变题目版本记录：发布时保存规格、用例、比较器配置、资源限制和 harness 版本；提交绑定具体版本，判题只读取绑定版本。
- 已发布版本不得原地改动；编辑并再次发布生成新版本。删除题目不删除历史判题依据。若选择提交快照替代版本表，先记录事务一致性和存储成本，再按同等验收标准实现。
- 历史提交无法还原的原始版本必须标记为不可精确复现，不能伪造历史快照。新版本号的并发分配需要数据库约束。

验收：匿名用户不能读草稿；普通用户不能提交草稿或读取隐藏数据；提交后改题，新旧提交各自使用绑定版本；并发发布不产生冲突版本。

### T08：沙箱资源控制与打包兼容

- 修复 Gson 库准备方式，支持最终 Boot JAR 中的嵌套依赖，或采用明确的独立运行库资源。缺少关键依赖时给出系统错误/启动失败，不能继续导致用户代码被误判编译错误。
- 检查 Linux Docker CPU 配额是否实际生效，不能仅以存在 `withCpuCount` 认定限核成功；采用目标平台支持的配额方式并做实测。
- 保留禁网、非 root、cap-drop、no-new-privileges、只读根目录及 PID/内存限制；固定判题镜像 digest，部署前校验镜像存在。
- 沙箱自行校验代码、文件、用例数、输入总量、资源参数上下界及总执行期限，不完全信任调用方；特别检查 V1/V2 两个入口的一致性。
- 限制沙箱同时运行的任务数；编译和运行均计入容量。输出截断、无限循环、内存耗尽必须有确定结果并及时释放资源。
- 容器加可识别标签，工作目录有明确所有权；启动/周期清理只处理本系统过期资源，并避开有效租约任务，禁止全局清理 Docker。
- 若沙箱服务自身容器化，验证 Docker daemon 看到的宿主机 bind mount 路径与沙箱生成路径一致；不可仅在应用容器内创建目录后假定宿主机可见。

验收：最终 JAR 在 Linux Docker 下完成 ACM/函数模式；恶意资源测试不能突破配置上限；并发达到上限后有明确过载响应；强杀后残留可回收；不误删其他容器和有效任务目录。

### T09：限流与容量预算

- 为登录/注册设置 IP 与账号维度限制，为提交设置用户/IP 频率、用户未完成提交配额；多实例环境下仍须生效。
- 提交代码长度在入库前校验，与数据库字段和沙箱约束对齐；JSON 请求体与用例总量应有明确上限，不能用 multipart 大小配置代替。
- 明确 MQ prefetch、消费者并发、沙箱执行槽位、HTTP 超时和任务租约关系。单次超时覆盖合法任务预算，同时不能允许无限等待。
- 积压超过阈值时拒绝新提交或明确排队，不先返回成功再无记录地丢弃。限流依赖故障采用有界降级，不能默认无限放行高成本接口。

验收：限流响应可被客户端识别且不产生多余提交记录；多实例无法绕过配额；压测记录吞吐、排队延迟、CPU/内存、队列深度与错误率。容量阈值根据测试机器测量，不虚构固定 QPS 承诺。

### T10：监控、日志与健康检查

- 建立存活与就绪检查：存活不因中间件临时故障触发无休止重启；就绪能反映当前服务的关键依赖和工作能力。
- 日志串联 requestId、submitId、eventId、执行代次；避免记录密码、凭据、完整源码、隐藏用例和完整 Session。
- 指标至少覆盖 outbox 待投递/最老等待时间、队列积压、租约过期、重试/死信、判题结果分布、沙箱槽位、磁盘及残留容器。
- 管理端点仅内部开放；指标标签不得使用每次不同的 submitId，避免高基数。配置日志轮转及告警触发、恢复条件。

验收：人为制造投递积压、沙箱不可用和磁盘压力时可观察并触发对应告警；一条提交可以追踪到投递、执行及最终状态，日志中没有敏感内容。

### T11：部署、备份及回滚手册

- 默认交付 Linux 单机/小规模部署模板及反向代理配置；应用和存储服务以明确网络隔离。生产拓扑变化时重新验证容量及 Docker 路径。
- 提供 `.env.example`、持久卷说明、镜像/产物版本清单、启动顺序、依赖就绪等待、初始化和管理员建立步骤。禁止预置通用管理员密码。
- 按先兼容数据库增量、后应用切换的顺序发布。消费者协议变动需要说明旧消息兼容；切换前暂停新提交并按策略排空或安全交接任务。
- 回滚优先回退应用产物；数据库回滚单独评估，不自动执行破坏性 down SQL。验证旧版本是否能读取新增数据和消息。
- 明确 MySQL 备份、恢复演练及数据保留；Redis Session 丢失的用户影响、MQ 恢复后 outbox 对账步骤都要说明。
- 记录单机故障域及实际可承诺的 RPO/RTO；未测量时写待确认，不宣称高可用。

验收：按文档可在干净测试主机部署；只公开预期端口；恢复备份后能查询历史提交；应用回滚演练成功且无任务永久悬挂。

### T12：自动化与最终验收

- 单元测试重点覆盖状态迁移、令牌校验、权限过滤、配置校验；集成测试覆盖真实 MySQL/RabbitMQ/Redis 交互；Docker 测试单列环境要求。
- CI 区分普通测试、集成测试和 Linux 沙箱测试。记录实际执行数，避免 JUnit 版本/插件配置导致静默跳过。
- 从最终产物执行下表用例，不以 IDE 运行或已有 target 产物替代。测试使用独立数据和队列，不连接生产。
- 更新本文件任务表，并生成 `record/pre-release-acceptance.md`，包含命令、环境、结果摘要、证据路径、剩余风险及发布结论。

## 6. 最低验收矩阵

| 编号 | 场景 | 必须满足 |
|---|---|---|
| A01 | 干净构建、最终 JAR 启动 | 应用均启动成功，测试实际执行 |
| A02 | 缺生产密钥/错误服务凭据 | 启动失败或请求被拒绝，无默认密钥放行 |
| A03 | 公网、网关和服务直连测试 | 内部接口和基础设施不被未授权访问 |
| A04 | 两实例并发注册相同账号 | 唯一账号，稳定业务响应 |
| A05 | 匿名/普通用户访问草稿及他人提交 | 权限与脱敏正确 |
| A06 | 入库后杀进程、MQ 断连或无路由 | outbox 最终补投或形成持久可处理失败 |
| A07 | 抢占后强杀、重复消息、迟到结果 | 有界恢复，旧令牌不能覆盖新结果 |
| A08 | 死信写库失败、重复/过期死信 | 可恢复，不丢处理记录，不覆盖成功结果 |
| A09 | 提交后修改并发布题目 | 原提交使用原版本，新提交使用新版本 |
| A10 | ACM/函数模式的 AC、WA、CE、TLE、MLE、OLE | 结果与预期一致，使用最终打包产物 |
| A11 | 无限输出、无限循环、超额进程与内存 | 资源有界，结果明确，任务后资源释放 |
| A12 | 多实例限流、峰值提交及长队列 | 配额有效，积压可观测，不拖垮主机 |
| A13 | 进程强杀后容器/目录清理 | 只清理本系统过期资源，不影响有效任务 |
| A14 | 登录/退出、Session、HTTPS、CORS/CSRF | 合法流程可用，跨站与越权请求受控 |
| A15 | 新库迁移、存量升级、备份恢复、应用回滚 | 数据可恢复，版本兼容，任务可收敛 |

最终发布门槛：T01—T12 已验收；上述场景有执行证据；无未处置的高风险安全问题；生产变量和网络方案已落实；回滚步骤经过演练。存在阻塞项时可以交付代码，但结论必须是“暂不发布”并明确剩余项。
