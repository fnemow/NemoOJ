# 网络边界与访问控制

本文定义 NemoOJ 的暴露面与访问控制策略，是 T04 的交付物，也是 T11 部署模板的依据。

## 1. 端口暴露矩阵

**只有网关的 HTTPS 入口对公网开放，其余全部限制在内部网络。**

| 服务 | 端口 | 暴露级别 | 说明 |
|---|---|---|---|
| 反向代理 / HTTPS 入口 | 443 | **公网** | 唯一对外入口，TLS 终止 |
| 网关 gateway | 8101 | 内部 | 只接受来自反向代理的连接 |
| 用户服务 user | 8102 | 内部 | 可被网关与内部服务访问 |
| 题目服务 question | 8103 | 内部 | 同上 |
| 判题服务 judge | 8104 | 内部 | 不应被网关直接暴露 |
| 沙箱 nemo-sandbox | 8090 | **仅判题服务可达** | 持有代码执行能力，暴露面最小化 |
| MySQL | 3306 | 内部 | 仅用户/题目服务可达 |
| Redis | 6379 | 内部 | Session 存储，仅 user/question 可达 |
| RabbitMQ | 5672 / 15672 | 内部 | 15672 管理台按需受控访问 |
| Nacos | 8848 / 9848 | 内部 | 控制台按需受控访问 |
| Docker daemon | 2375 / 2376 | **绝不可对公网开放** | 等价于主机 root，仅沙箱所在主机本地可达 |

实现方式见本目录的 `docker-compose.yml` 与 `nginx/oj.conf`（容器网络 + 反向代理）。
拓扑已通过 YAML 解析核对：**只有 proxy 发布 80/443**；应用服务同时接入
`app`（互相调用）与 `data`（访问存储）；存储只接 `data`；
沙箱只接 `sandbox`，仅判题服务跨界可达。要点：

- 用 Docker 自定义网络让服务之间互通，**不使用 `ports` 发布内部服务**，只用 `expose`；
- 仅反向代理与网关发布端口；
- 沙箱不加入与网关同网段，只与判题服务共享网络；
- 管理控制台（RabbitMQ / Nacos）默认不发布端口，需要时通过 SSH 隧道访问。

> 本机开发环境（Windows，各服务直接监听 0.0.0.0）**不满足**上述边界，
> 仅用于联调，不能作为生产部署方式。

## 2. 内部接口（`/inner/**`）防护

内部接口暴露的是不受终端用户权限约束的能力（按 id 读用户、按 id 写提交状态、触发判题）。
因此设三层，任一层失效都不会直接导致越权：

| 层 | 位置 | 行为 |
|---|---|---|
| 1. 入口阻断 | 网关 `GlobalAuthFilter` | `/**/inner/**` 一律 403 |
| 2. 凭据剥离 | 网关 `GlobalAuthFilter` | 删除外部请求携带的 `X-Internal-Token`，防止伪造透传头 |
| 3. 服务端独立校验 | 各业务服务 `InternalAuthFilter` | `/inner/*` 必须携带正确凭据，否则 403 |

**第 3 层是必需的，不能只靠网关**：业务服务端口在内网仍可能被同网段进程直接访问
（调试端口、误配的端口映射、内网横向移动）。验收时已实测绕过网关直连 8102 的场景。

凭据约定：

- 请求头 `X-Internal-Token`，取值来自环境变量 `INTERNAL_AUTH_SECRET`；
- **所有业务服务必须配置为同一个值**，长度 ≥ 16；
- 服务端使用常量时间比较；缺少或错误一律 403，不区分二者，避免给出探测反馈；
- Feign 调用方由 `InternalAuthFeignInterceptor` 统一附加，业务代码无需处理；
- 生产未配置该变量时**启动失败**，不会在无凭据状态下运行。

**常见误解**：通过第 3 层校验只说明"调用方是内部服务"，**不代表终端用户已登录**。
公共接口仍必须自行做登录与角色校验，服务凭据不能替代用户权限判断。
已实测确认：带正确内部凭据访问 `/api/user/get/login` 仍返回"未登录"。

### 内部接口的返回值收敛

`/inner/get/id`、`/inner/get/ids` 会把 `userPassword` 置空后再返回。
调用方（题目/判题服务）只需要角色、昵称、头像，没有任何一处依赖密码散列。
少传一份散列，就少一处可能落到对方日志、堆转储或异常报文里的敏感数据。

## 3. CSRF 防护策略

本系统使用 **Cookie + Session** 认证，浏览器会自动携带 Cookie，因此存在 CSRF 风险。

**明确一点：CORS 白名单不是 CSRF 防护。** CORS 只限制跨域*读取*响应；
攻击者并不需要读到响应，只要请求发得出去就够了。把 CORS 当作 CSRF 防线是常见误解。

实际采用以下机制，**按重要性排序**（下面的顺序反映实测的拦截效果，不是设计意图）：

| 顺序 | 机制 | 作用 | 实测证据 |
|---|---|---|---|
| 1 | Cookie `SameSite=Lax`（prod 配置） | 浏览器层面阻断跨站请求携带 Cookie。**这是最有效的一层** | 需浏览器验证，本地未覆盖 |
| 2 | CORS 层 `CorsWebFilter` | 任何携带非白名单 `Origin` 的请求直接 403，**不限方法** | `GET + 非法 Origin` → 403（且路径不存在也 403，说明在路由前就被拦下） |
| 3 | 网关 `CsrfOriginFilter` | 对 POST/PUT/PATCH/DELETE 独立校验 `Origin` | `POST + 非法 Origin` → 403；`POST + 后缀伪装域名` → 403 |
| 4 | Cookie `HttpOnly` + `Secure` | 降低 Cookie 被脚本读取与明文回传的风险 | — |

**关于第 3 层，需要说清楚它到底是什么**：实测发现 CORS 层已经会拒绝非白名单来源，
且对所有方法生效。也就是说第 3 层在当前配置下与 CORS 的检查**重叠**，
它属于"独立实现的同一策略"，而不是唯一的 CSRF 防线。

保留它的理由：CORS 的检查来自 Spring 的 CORS 实现，会随 CORS 配置一起变化
（例如将来有人放宽或调整 `registerCorsConfiguration` 的作用路径），
而写方法的来源校验应当由网关自己显式持有，不依赖另一个组件的副作用。

`CsrfOriginFilter` 的取舍：

- 不带 `Origin` 的请求（curl、服务间 Feign 调用）放行——
  CSRF 的前提是"浏览器自动附带凭据"，这类请求不满足前提，
  且它们仍受登录态与内部凭据约束；
- GET 不校验（按 HTTP 语义不应改状态）。若将来出现用 GET 改数据的接口，
  应改接口设计，而不是放宽这里。

**结论**：不能因为配置了 CORS 白名单就认为 CSRF 已解决——
真正阻断 CSRF 的是 `SameSite=Lax` 与"服务端拒绝非白名单来源"这两件事共同作用。
`SameSite=Lax` 尚未在真实浏览器中验证（本地无 HTTPS 与域名），列为待验证项。

## 4. 权限模型

| 类型 | 判定方式 | 位置 |
|---|---|---|
| 是否登录 | Session 中的 `USER_LOGIN_STATE` | 各服务 `getLoginUser(request)` |
| 是否管理员 | `userRole == admin` | `@AuthCheck(mustRole = ADMIN_ROLE)` AOP |
| 是否本人 | 比较 `userId` 与登录用户 id | 各业务方法内 |

`AuthInterceptor` 对 `@AuthCheck` 注解生效，被封号（`ban`）用户直接拒绝。
`/inner/**` 不走该注解——它的调用方是服务而非用户。

## 5. 上线前检查清单

- [ ] 只有反向代理的 443 对公网开放，`docker ps` 中内部服务无 `0.0.0.0:port->` 映射
- [ ] Docker daemon 未监听 TCP（或仅 unix socket），未被安全组放行
- [ ] RabbitMQ / Nacos 管理台未对公网开放
- [ ] `INTERNAL_AUTH_SECRET` 在所有业务服务中一致，且不是 `dev-only-internal-token`
- [ ] `SANDBOX_SECRET` 在判题服务与沙箱中一致，长度 ≥ 16
- [ ] `CORS_ALLOWED_ORIGINS` 为真实域名，不含 `*`
- [ ] HTTPS 已启用，Cookie `Secure` 生效
- [ ] 直连 8102/8103/8104 的 `/inner/**` 返回 403（无凭据与错误凭据均试）
- [ ] 经网关访问 `/api/*/inner/**` 返回 403
